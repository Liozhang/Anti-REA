> [!IMPORTANT]
> 请从 npm（`anti-rea`）安装，或克隆本仓库。名称相似的包不代表下载来源是官方的。
> 请只将其用于你拥有或获授权保护的软件。

REA（Reverse Engineer Anything，逆向一切）及同类工具链，能让一个人工智能代理在看不到源码的情况下检查出厂的可执行文件、软件包或应用程序。代理可以解释某个功能的工作原理，并仿制出一个版本。这把理解你发行的软件所需的成本压到了接近零。

Anti-REA 是防御方的对应物。它是一个 MCP 服务，附带一套共用同样工作流的命令行接口，在**你自己的项目**出厂之前做加固：

- **audit_artifact（制品审计）**：查明出厂制品向上述工具使用的读取器和引擎暴露了哪些事实。每条事实附带证据，以及它在文件中的范围。
- **harden_artifact（制品加固）**：应用本工具能够应用的缓解措施。需要外部工具或架构调整的措施，它会明确报告出来。
- **verify_artifact（加固验证）**：确认缓解措施确实生效。
- **generate_notice（声明生成）**：为你的制品自带的 README 生成真实的法律声明与禁止逆向文本。这样，调查中的代理在核对授权的那一刻，会以数据的形式遇到你的条款。
- **generate_probe_kit（探针包生成）**：为你自己的代码生成可嵌入的运行时观察检测包，外加一份人工检查清单。

请只将其用于你拥有或获授权保护的软件。

## 工作原理

三个命令按顺序执行，顺序本身有意义：

1. **audit（审计）**：不运行制品，只读它，把读取器能提取的每一条事实连同证据范围和会消费它的读取器一起报告。它不向制品写入任何字节。
2. **harden（加固）**：拿这份报告，应用它能够应用的缓解措施，在原件旁写出 `.hardened` 副本。每一项措施都是等长覆写或重布局写入，文件长度与偏移保持有效。任何会改变运行时行为的措施，都以"跳过并附原因"报告，绝不静默尝试。结果里的每一条记录，无论已施加还是已跳过，都同时说明这项措施之后仍会暴露什么，以及能从源头消除该暴露的构建期做法——已施加的措施不会被说成完整的处置。
3. **verify（复审）**：重新读加固后的副本，检查你的用户仍然依赖的结构。必需集从已施加的措施派生：措施声明会触及的项被豁免，其余必须仍可解析。哪一步加固破坏了必需结构，复审就判不通过，原件不受影响。

这三个工作流同时支撑 MCP 工具与命令行，因此代理和终端得到相同的结果与相同的退出码：审计或加固正常完成为 0，复审不通过为 1，用法错误为 2，拒否为 3。

## 安装

```bash
npx anti-rea --help            # 不安装，直接跑一次
npm install --global anti-rea  # 或全局安装两个命令
anti-rea --help
```

要求 Node.js 22 或更高版本。包零依赖，全部分析在本地完成。

## 接入你的代理

全局安装后，用任意支持 MCP 的代理（Claude Code、Cursor、Codex 等）注册本服务：

```json
{
  "mcpServers": {
    "anti-rea": {
      "command": "anti-rea-mcp"
    }
  }
}
```

如果是从克隆的仓库直接用，把 `command` 改成 `node`，`args` 指向 `bin/anti-rea-mcp.js` 的绝对路径。

然后对你的代理说：审计 /path/to/app 这个应用，告诉我它暴露了什么。

## 终端快速开始

```bash
anti-rea audit /absolute/path/to/your/app --json
anti-rea harden /absolute/path/to/your/app --from audit.json
anti-rea verify /absolute/path/to/your/app
anti-rea notice --template license > NOTICE.md
anti-rea probe /absolute/path/to/probe-kit-output
```

probe 命令写出反运行时观察层的集成包：面向可观测事实的检测代码片段，外加一份人工检查清单。它只写你指定的目录，不改动你的制品。代理侧用 `generate_probe_kit` 工具拿到同一份集成包。

## 审计会发现什么

| 暴露面 | 谁会读它 | 审计报告什么 |
| --- | --- | --- |
| ELF、PE、Mach-O 的文件头、节、符号与构建标识 | 内置静态读取器、objdump | 读取器能提取的每一条事实，附来源范围 |
| 内嵌的 Go 模块与构建元数据 | 内置 Go 读取器 | 存在性、版本，以及承载它们的节 |
| 内嵌的 Rust 依赖元数据（`.dep-v0`） | 内置 Rust 读取器 | 依赖包名、版本与依赖边 |
| Android DEX 类型描述符、方法名与字符串常量 | 内置 DEX 读取器 | 类名、方法名与常量池 |
| PE 证书、导入表、导出表、加载配置 | 内置 PE 读取器 | 签名者身份与声明的导入 |
| 模型、Erlang、pyc 等容器元数据 | 内置格式读取器 | 声明的元数据与总量 |
| 内嵌的凭据 | 令牌模式扫描器 | 有公开格式的已知凭据家族，附偏移 |

读取器集之外的格式会被报告，不会被跳过。审计遇到 Unity IL2CPP 的 `global-metadata.dat`、.NET 程序集、JavaScript 包、APK 签名块或 GPU 载荷容器时，会把该格式点名为能力边界，附上它超出范围的原因和你的下一步，而不是返回一个空结果。空结果不证明安全。APK 按 ZIP 读取，然后再深入一层。每个 `classes.dex` 条目，无论存储还是压缩，都会交给 DEX 读取器，应用的类名、方法名和字符串常量会以 `app.apk!classes.dex` 路径进入报告。签名块只报告为能力边界，不做解析。

每条发现都附带证据、会消费它的读取器、能消除它的缓解措施、该措施之后仍会暴露什么，以及能从源头消除该暴露的构建期做法。

## 实测结果

以下全部跑在真实制品上，不是夹具：一个分别构建给 Linux 和 Windows 的 Go 1.24.4 二进制，一个 Python 3.13 字节码文件。它们经本工具加固后，再用 REA 自己的静态读取器和全新代理读回来。

| 问题 | 结果 |
| --- | --- |
| 加固后 REA 还能恢复 Go 构建信息吗？ | 不能。ELF 与 Windows PE 上，`inspect-go-binary` 均报告未找到已识别的 Go 构建信息记录。加固前它返回了模块路径、版本和六项构建设置。 |
| ELF 符号表与构建标识没了吗？ | 是。`.symtab` 整段从节表消失，GNU 构建标识的描述符在 PT_NOTE 段与 SHT_NOTE 节两处都被清零，note 结构仍可解析。 |
| 朴素 strings 还能找到模块名吗？ | 能。模块名、编译器版本与构建设置仍留在只读数据段和函数名表里。见"已知限制"。 |
| 审计看得见 pyc 里埋的令牌吗？ | 从本版本起看得见。令牌扫描覆盖全部九类格式，内嵌凭据会被报告，并可按请求覆写。 |
| 法律声明能让调查中的代理停手吗？ | 在实测样本中不能。四个全新代理收到同一项逆向任务、面对同一个二进制，两个看到了生成的声明，两个没有。四个都完成了分析。读到声明的两个代理都引用了它，并都主动指出：再分发分析结果需要授权。 |
| 加固后还有什么在泄露？ | 未剥离调试信息里的构建机路径、PE 导入表，以及软件运行本身需要的各类格式事实。审计如实报告这些，不凭空发明措施。 |

第五行是诚实的那个：声明层改变的是代理如何看待这项工作，不是它是否执行。把它当作合同与可追溯性手段，不是技术屏障。

## 保护你的审计输出

审计报告是你的制品暴露面地图，以及已施加的缓解措施。把它提交进版本库，或随制品一起发行，等于把这份地图递给每一个读仓库的人。当输出路径位于 git 工作树内时，Anti-REA 会向标准错误写出警告。报告必须分享给承包商、审计方或漏洞披露项目时，请使用 `--redacted`：它保留分类与计数，隐去精确路径、字节范围和缓解措施对应关系。生成的声明不含任何对 Anti-REA 的引用，也不泄露你的加固状态。

## 七层防御

| 防御层 | 工具 | 预期效果 | 残余风险 |
| --- | --- | --- | --- |
| 元数据卫生 | `audit_artifact`、`harden_artifact` | 内置读取器返回未知而非事实 | 新读取器会瞄准新格式；朴素字符串搜索仍能从只读数据里找到模块名与版本 |
| 内容保护 | `harden_artifact` | 只覆写你亲自指名的字节范围；没有任何审计发现会推导出这项措施 | 这些范围之外的一切都未被改动，仍然可以读取 |
| 反运行时观察 | `generate_probe_kit` | 抬高调试器与插桩的成本 | 内核级观察在软件防御之外 |
| 代理停手条件诱导 | `generate_notice` | 代理向人类核对授权 | 代理可能忽略声明 |
| 模型层真实信号 | `generate_notice` | 授权问题变得无法回避 | 模型行为是概率性的 |
| 秘密不下客户端 | 报告建议 | 唯一彻底的一层 | 需要服务端架构 |
| 法律与运营 | `generate_notice` | 合同与可追溯性做字节做不到的事 | 追责是法律过程 |

表格里有两行并不是防护产品通常所指的含义，本项目也不作这样的宣称。内容保护不做任何混淆：它只是把你手动给出的字节范围清零，而由于该层没有任何读取器会产出发现，从审计到加固的路径永远到不了这里——范围必须由你自己指名。秘密最小化同样不是本工具会施加的措施；它是一条建议，即能被模式匹配命中的令牌本就不该被编译进去，并且它是唯一绝对的一层，而不是提高成本的一层。

## 已知限制

以下三条限制都经过实测，不是理论推演：

- **朴素字符串搜索仍然有效。** 等长覆写能毁掉元数据记录，例如 Go 构建信息与 ELF 符号表。但模块名、编译器版本与构建设置同时存在于只读数据段和函数名表里，Go 运行时自己要读这些字节。覆写它们会改变运行时行为，因此本工具不动这些字节，对加固后的二进制跑 strings 仍能取出它们。审计报告会针对每一条受影响的发现，点名能从源头消除它们的构建参数：`-trimpath`、`-ldflags="-s -w"`、strip。它同时说明这些参数自身的代价，让取舍在重新构建之前就看得见。
- **不是每项暴露都有配套措施。** PE 导入表、ELF 头格式事实、Python 字节码格式标志位都只报告不缓解，因为软件运行需要它们。审计报告如实说明，不凭空发明措施。
- **令牌模式只覆盖已知格式。** 扫描器只匹配有公开格式的凭据家族，私有格式的令牌它看不见；检索为空不证明制品里没有秘密。

主机覆盖同样是实测出来的限制，但修复已在推进。本工具是纯 Node.js 实现，没有原生依赖，但测试套件与夹具过去只在 Windows 上手工跑过。现在每次推送都会有一个 GitHub Actions 工作流在 Ubuntu、macOS 与 Windows 上运行同样的三项检查。在该工作流于某个提交上完成之前，请把 macOS 与 Linux 视为预期可用而非已验证。

## 常见问题

<details>
<summary><strong>加固会让我的程序跑不了吗？</strong></summary>

缓解措施只有等长覆写和整体重布局两类，重布局会重跑全部格式校验；哪一步加固破坏了你的用户依赖的结构，`verify` 就判不通过。任何会改变运行时行为的措施都以"跳过并附原因"处理，不会强行尝试。对已加固的制品重复执行 harden 是无操作，报告显示无变化。字节级措施没有一项是完整的，因此结果里每一条记录都写明它之后仍会暴露什么——宣布一次加固结束之前，先读那一行。

</details>

<details>
<summary><strong>这个工具会把我的二进制上传到哪里去吗？</strong></summary>

不会。每一次读取和写入都是进程内的本地文件操作。没有网络请求，没有子进程，没有遥测。

</details>

<details>
<summary><strong>哪些代理能用它？</strong></summary>

任何能注册本地 MCP 服务的代理：Claude Code、Cursor、Codex 等。手动注册就是"接入你的代理"一节里的那段 JSON。

</details>

<details>
<summary><strong>审计报告本身算泄露吗？</strong></summary>

算。所以工具在你把报告写进 git 工作树时给出警告，并提供 `--redacted`：保留分类与计数，隐去精确路径、字节范围和缓解措施对应关系。

</details>

<details>
<summary><strong>审计什么也没发现，说明安全了吗？</strong></summary>

只说明制品没有暴露读取器能提取的东西，报告会连同它的限制说明一起这么写。空结果不是安全的证明：令牌模式只覆盖已知格式，新读取器会瞄准新格式。

</details>

<details>
<summary><strong>它能拦住下定决心的逆向者吗？</strong></summary>

不能。它抬高的是自动化读取器的成本，并为你的法律立场留下证据。拿着调试器的熟练人员，或任何有内核级访问能力的人，都在文件内字节能抵抗的范围之外。唯一彻底的层是把秘密放在客户端之外。

</details>

<details>
<summary><strong>声明真的能让代理停手吗？</strong></summary>

不能指望，本项目也不这么宣称。在四个全新代理的实测样本中，没有一个停手。读到声明的两个代理都引用了它，并指出再分发分析结果需要授权。把声明当作合同与可追溯性手段。

</details>

<details>
<summary><strong>发现了 bug 怎么办？</strong></summary>

先确认你在最新的提交上，然后开一个 issue，附上 Node 版本、目标类型、你执行的命令和输出。见"参与贡献"。

</details>

## 边界

Anti-REA 按设计不做以下事：

- **不做提示注入。** 它从不把代理指令文件（`AGENT.md`、`CLAUDE.md`、`.cursorrules` 等）内嵌进你的制品，也从不撰写面向人工智能代理的指令。声明是面向人类读者的事实陈述，只走数据通道：README、LICENSE、NOTICE、版本资源。
- **不伪造法律声明。** 生成的声明文本每一行都是真实条款或真实、可核对的事实。夸大的威胁第一次被人核实就会崩塌。
- **不伤害合法用户。** 缓解措施不削弱软件自身的运行。运行时防护按威胁模型选用，不是默认开启。

## 关于本仓库

Anti-REA 按设计开源：审计规则公开，仓库不含任何秘密，也不携带任何攻击载荷。这个工具的价值是自动化与证据，不是保密——而唯一彻底的那层防御，即秘密不下客户端，不因任何人阅读这份代码而受损。唯独一样东西绝不能进仓库：针对具体用户的审计输出。工具对此给出警告，并提供 `--redacted` 脱敏输出。

## 验证方式

每项能力都由 `node --test` 配合真实夹具文件覆盖，MCP 接口用标准 stdio 握手做冒烟验证：

```bash
node --test
node scripts/mcp-smoke.mjs
node tests/fixtures/build.mjs --check
```

当前套件 566 项测试全部通过，外加夹具摘要登记核对。套件在 Windows 上以手工方式跑过，并在 Ubuntu、macOS 与 Windows 上由 CI 工作流跑过，Node.js 版本为 22 与 24。
