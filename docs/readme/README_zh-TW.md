> 請只從本儲存庫取得 Anti-REA。它還沒有 npm 版本，名稱相似的套件不代表下載來源是官方的。
> 請只把它用在你擁有或獲授權保護的軟體上。

REA（Reverse Engineer Anything，逆向一切）與同類以 MCP 為基礎的工具鏈，能讓 AI 代理程式在看不到原始碼的情況下，檢查出貨的二進位檔、軟體套件或應用程式，解釋某項功能如何運作，再仿製出一個版本。這把你理解自家發行軟體的成本壓到接近零。

Anti-REA 是防禦方的對應工具。它是一套 MCP 服務，附帶一套共用相同工作流程的命令列介面，在**你自己的專案**出貨前完成強化：

- **audit_artifact**：出貨成品向這類工具使用的讀取器與引擎暴露了什麼，每一項事實都附上證據，以及它在檔案中的範圍
- **harden_artifact**：套用本工具能套用的緩解措施，並回報哪些措施需要外部工具或架構層級的調整
- **verify_artifact**：確認緩解措施確實生效
- **generate_notice**：為成品自帶的 README 產生真實的授權條款與禁止逆向工程文字，讓執行調查的代理程式在核對授權的那一刻，以資料的形式遇到你的條款
- **generate_probe_kit**：一套可嵌入你自己程式的執行階段觀察偵測包，外加一份人工檢查清單

## 運作方式

三個命令依序執行，而順序本身很重要：

1. **`audit`** 不執行你的成品，只讀取它，回報讀取器能提取的每一項事實，每項都附上證據範圍，以及會消費它的讀取器。它不向成品寫入任何位元組。
2. **`harden`** 取得這份報告，套用它能套用的緩解措施，在原件旁寫出 `.hardened` 副本。每一項緩解措施都是等長覆寫或重新佈局寫入，檔案長度與偏移保持有效。任何會改變執行階段行為的措施，都會連同原因一併回報為已跳過，絕不靜默嘗試。結果裡的每一條記錄，無論已套用或已跳過，都同時說明這項措施之後仍會暴露什麼，以及能從源頭消除該暴露的建置時期做法——已套用的措施不會被說成完整的處置。
3. **`verify`** 重新讀取強化後的副本，檢查你的使用者仍然依賴的結構。必需集合由已套用的緩解措施推導得出：措施聲明會觸及的項目予以豁免，其餘全部仍須可解析。哪一趟強化破壞了必需結構，審查就判不通過，原件保持不動。

MCP 工具與命令列介面背後是同樣三個工作流程，因此代理程式與終端機得到相同結果與相同結束碼：稽核或強化正常完成為 0，驗證失敗為 1，用法錯誤為 2，拒絕執行為 3。

## 連接你的代理程式

用任何支援 MCP 的代理程式（Claude Code、Cursor、Codex 等）註冊這套服務：

```json
{
  "mcpServers": {
    "anti-rea": {
      "command": "node",
      "args": ["/absolute/path/to/Anti-REA/bin/anti-rea-mcp.js"]
    }
  }
}
```

然後對你的代理程式說：*稽核 /path/to/app 這個應用程式，告訴我它洩漏了什麼。*

## 終端機快速開始

```bash
node bin/anti-rea.js audit /absolute/path/to/your/app --json
node bin/anti-rea.js harden /absolute/path/to/your/app --from audit.json
node bin/anti-rea.js verify /absolute/path/to/your/app
node bin/anti-rea.js notice --template license > NOTICE.md
node bin/anti-rea.js probe /absolute/path/to/probe-kit-output
```

`probe` 命令寫出執行階段觀察防護層的整合包：針對可觀測事實的可嵌入偵測片段，外加一份人工檢查清單。它只寫入你指定的目錄，絕不修改你的成品。代理程式可透過 `generate_probe_kit` 工具取得同一份整合包。

## 稽核會回報什麼

| 暴露面 | 誰會讀它 | 稽核回報什麼 |
| --- | --- | --- |
| ELF/PE/Mach-O 檔頭、區段、符號與建置識別碼 | 內建靜態讀取器、objdump | 讀取器能提取的每一項事實，附來源範圍 |
| 內嵌的 Go 模組與建置中繼資料 | 內建 Go 讀取器 | 是否存在、版本，以及承載它們的區段 |
| 內嵌的 Rust 依賴中繼資料（`.dep-v0`） | 內建 Rust 讀取器 | 套件名稱、版本與依賴邊 |
| Android DEX 型別描述元、方法名稱與字串常數 | 內建 DEX 讀取器 | 類別名稱、方法名稱與常數池 |
| PE 憑證、匯入、匯出與載入組態 | 內建 PE 讀取器 | 簽署者身分與宣告的匯入 |
| 模型、Erlang、pyc 等容器中繼資料 | 內建格式讀取器 | 宣告的中繼資料與總計 |
| 內嵌的認證資料 | 權杖樣式掃描器 | 具公開格式的已知認證資料家族，附偏移 |

讀取器集之外的格式會被回報，不會被跳過。稽核遇到 Unity IL2CPP 的 `global-metadata.dat`、.NET 組件、JavaScript 打包檔、APK 簽署區塊或 GPU 酬載容器時，會把該格式點名為能力邊界，連同它超出支援範圍的原因與你的下一步，而不是回傳空結果。空結果不是安全的證明。APK 以 ZIP 形式讀取，然後再深入一層。每個 `classes.dex` 條目，無論是儲存還是壓縮，都會交給 DEX 讀取器，應用程式的類別名稱、方法名稱與字串常數會以 `app.apk!classes.dex` 路徑進入報告。簽署區塊只回報為能力邊界，不解析。

每一項發現都附上證據、會消費它的讀取器、能消除它的緩解措施、該措施之後仍會暴露什麼，以及能從源頭消除該暴露的建置時期做法。

## 實測結果

以下全部跑在真實成品上，不是測試資料：一個分別為 Linux 與 Windows 建置的 Go 1.24.4 二進位檔，和一個 Python 3.13 位元組碼檔案。它們經本工具強化後，再用 REA 自己的靜態讀取器與全新的代理程式讀回來。

| 問題 | 結果 |
| --- | --- |
| 強化後 REA 還能還原 Go 建置資訊嗎？ | 不能。在 ELF 與 Windows PE 上，`inspect-go-binary` 都回報找不到已識別的 Go 建置資訊記錄。強化前它會回傳模組路徑、版本與六項建置設定。 |
| ELF 符號表與建置識別碼消失了嗎？ | 是。`.symtab` 整個從區段表消失，GNU 建置識別碼在 PT_NOTE 節與 SHT_NOTE 區段兩處都被清零，note 結構仍可解析。 |
| 純粹的 `strings` 還找得到模組名稱嗎？ | 找得到。模組名稱、編譯器版本與建置設定仍留在唯讀資料與函式名稱表中。見「已知限制」。 |
| 稽核看得見藏在 Python 位元組碼中的權杖嗎？ | 看得見，自本次發布起。權杖掃描器跑遍全部九種格式，內嵌的認證資料會被回報，也可應要求覆寫。 |
| 法律聲明能讓執行調查的代理程式停手嗎？ | 在實測樣本中不能。四個全新代理程式收到同一項逆向工程任務、面對同一個二進位檔；兩個看到了產生的聲明，兩個沒有。四個都完成了分析。兩個讀到聲明的代理程式都引用了它，並都主動指出再散佈分析結果需要授權。 |
| 強化之後還有什麼在洩漏？ | 未剝離除錯資訊中的建置機器路徑、PE 匯入表，以及軟體運行所需的各種格式事實。稽核如實回報這些，不發明緩解措施。 |

第五列是誠實的那一列：聲明層改變的是代理程式如何看待這項工作，而不是它是否執行。把它當成合約與可追溯性手段，不是技術屏障。

## 保護你的稽核輸出

稽核報告是一張你的成品暴露面地圖，以及已套用的緩解措施。把它提交進版本控制，或放進成品裡一起出貨，等於把這張地圖交給任何讀儲存庫的人。當輸出路徑位於 git 工作樹內時，Anti-REA 會向標準錯誤輸出寫出警告。報告必須分享給承包商、稽核人員或弱點揭露計畫時，請使用 `--redacted`：它保留分類與計數，略過確切路徑、位元組範圍與緩解措施對應關係。產生的聲明不含任何對 Anti-REA 的參照，也不透露你的強化狀態。

## 防禦層級

| 層級 | 工具 | 預期效果 | 殘餘風險 |
| --- | --- | --- | --- |
| 中繼資料衛生 | `audit_artifact`、`harden_artifact` | 內建讀取器回傳未知而非事實 | 新讀取器可以鎖定新格式；純字串搜尋仍能從唯讀資料中找到模組名稱與版本 |
| 內容保護 | `harden_artifact` | 只會覆寫你親自指名的位元組範圍；沒有任何稽核發現會推導出這項措施 | 這些範圍之外的一切都未被改動，仍然可以讀取 |
| 執行階段觀察防護 | `generate_probe_kit` | 提高除錯器與插樁的成本 | 核心層級的觀察超出可及範圍 |
| 代理程式停手條件引導 | `generate_notice` | 代理程式向人類確認授權 | 代理程式可能忽略聲明 |
| 模型層級真實訊號 | `generate_notice` | 授權問題變得無法迴避 | 模型行為是機率性的 |
| 秘密最小化 | 報告建議 | 唯一絕對有效的一層 | 需要伺服器端架構 |
| 法律與營運 | `generate_notice` | 合約與可追溯性能做到位元組做不到的事 | 執法是法律程序 |

表格裡有兩行並不是防護產品通常所指的含義，本專案也不作這樣的宣稱。內容保護不做任何混淆：它只是把你手動給出的位元組範圍清零，而由於該層沒有任何讀取器會產出發現，從稽核到強化的路徑永遠到不了這裡——範圍必須由你自己指名。秘密最小化同樣不是本工具會施加的措施；它是一條建議，即能被模式比對命中的權杖本就不該被編譯進去，並且它是唯一絕對的一層，而不是提高成本的一層。

## 已知限制

三項限制都經過實測，不是理論推演：

- **純字串搜尋仍然有效。** 等長覆寫能摧毀 Go 建置資訊與 ELF 符號表這類中繼資料記錄。但模組名稱、編譯器版本與建置設定同時也存在於唯讀資料與函式名稱表中，Go 執行階段本身就要讀這些位元組。覆寫它們會改變執行階段行為，因此 Anti-REA 不動這些位元組，任何對強化後二進位檔執行 `strings` 的人仍能取回它們。稽核報告會針對每一條受影響的發現，點名能從源頭消除它們的建置參數：`-trimpath`、`-ldflags="-s -w"`、`strip`。它同時說明這些參數自身的代價，讓取捨在重新建置之前就看得見。
- **不是每項暴露都有對應的緩解措施。** PE 匯入表、ELF 檔頭事實與 Python 位元組碼格式旗標，都只回報不緩解，因為軟體運行需要它們。稽核如實說明，不發明措施。
- **權杖樣式只涵蓋已知格式。** 掃描器比對具公開格式的認證資料家族。私有格式的權杖它看不見，而查無結果不證明成品中沒有秘密。

主機覆蓋率同樣是一項實測出的限制，但已有修復正在進行。本工具是純 Node.js，沒有原生依賴，但測試套件與測試資料過去只在 Windows 上以手動方式執行過。現在每次推送都會有一個 GitHub Actions 工作流程於 Ubuntu、macOS 與 Windows 上執行同樣的三項檢查。在該工作流程於某個提交上完成之前，請將 macOS 與 Linux 視為預期可用，而非已經驗證。

## 常見問題

<details>
<summary><strong>強化會讓我的應用程式壞掉嗎？</strong></summary>

緩解措施只有等長覆寫與整體重新佈局兩類，後者會重跑每一項格式檢查；哪一次強化破壞了你的使用者依賴的結構，`verify` 就判不通過。任何會改變執行階段行為的措施，都會連同說明的原因一併跳過，不會硬行嘗試。對已強化的成品重跑 `harden` 是無操作，回報顯示沒有變化。位元組層級的措施沒有一項是完整的，因此結果裡每一條記錄都寫明它之後仍會暴露什麼——宣布一次強化結束之前，先讀那一行。

</details>

<details>
<summary><strong>這個工具會把我的二進位檔上傳到別處嗎？</strong></summary>

不會。每一次讀取與寫入都是行程內的本機檔案操作。沒有網路請求、沒有子行程、沒有遙測。

</details>

<details>
<summary><strong>哪些代理程式能用它？</strong></summary>

任何能註冊本機 MCP 服務的代理程式：Claude Code、Cursor、Codex 等。手動註冊就是「連接你的代理程式」一節下的那段 JSON。

</details>

<details>
<summary><strong>我的稽核報告本身算洩漏嗎？</strong></summary>

算。所以工具在你把報告寫進 git 工作樹時提出警告，並提供 `--redacted`：保留分類與計數，略過確切路徑、位元組範圍與緩解措施對應關係。

</details>

<details>
<summary><strong>如果稽核什麼都沒找到呢？</strong></summary>

那表示成品沒有暴露讀取器能提取的任何東西，報告會連同它的限制如實寫明。空結果不是安全的證明：權杖樣式只涵蓋已知的認證資料格式，而新讀取器可以鎖定新格式。

</details>

<details>
<summary><strong>它擋得下定決心的逆向工程者嗎？</strong></summary>

擋不住。它提高的是自動化讀取器的成本，並為你的法律立場留下證據。拿著除錯器的熟手，或任何有核心層級存取權的人，都在檔案中的位元組能抵抗的範圍之外。唯一絕對有效的一層，是把秘密留在用戶端之外。

</details>

<details>
<summary><strong>聲明真的能讓代理程式停手嗎？</strong></summary>

不能指望，本專案也不如此宣稱。在四個全新代理程式的實測樣本中，沒有一個停手。兩個讀到聲明的代理程式都引用了它，並標示再散佈分析結果需要授權。把聲明當成合約與可追溯性手段。

</details>

<details>
<summary><strong>我發現了 bug，接下來呢？</strong></summary>

先確認你位於最新的提交上，然後開一個 issue，附上你的 Node 版本、目標類型、你執行的命令與輸出。見「參與貢獻」。

</details>

## 邊界

Anti-REA 依設計不做以下幾件事：

- **沒有提示注入。** 它絕不把代理程式指令檔（`AGENT.md`、`CLAUDE.md`、`.cursorrules` 等）放進你的成品，也絕不撰寫指向 AI 代理程式的指令。聲明是寫給人類讀者的事實陳述，只透過資料通道傳遞：README、LICENSE、NOTICE、版本資源。
- **沒有捏造的法律主張。** 產生的聲明文每一行都是真實條款，或真實且可核查的事實。誇大的威脅，第一次被人查證就會崩解。
- **不傷害合法使用者。** 緩解措施絕不削弱你的軟體自身運作。執行階段防護依威脅模型選用，不是預設值。

## 關於本儲存庫

Anti-REA 依設計開源：稽核規則公開，不持有任何秘密，也不攜帶任何攻擊載荷。這工具的價值是自動化與證據，不是保密——而唯一絕對有效的防禦層，也就是把秘密留在用戶端之外，不會因為任何人閱讀這份程式碼而受影響。唯一絕不能進儲存庫的東西，是針對特定使用者的稽核輸出；因此工具對此提出警告，並提供 `--redacted`。

## 驗證

每一項功能都由 `node --test` 搭配真實測試檔案覆蓋，MCP 介面則以標準 stdio 握手做冒煙測試：

```bash
node --test
node scripts/mcp-smoke.mjs
node tests/fixtures/build.mjs --check
```

目前測試套件共 592 項測試，全部通過，外加測試資料摘要登記核對。套件在 Windows 上以手動方式執行過，並在 Ubuntu、macOS 與 Windows 上由 CI 工作流程執行過，Node.js 版本為 22 與 24。

歡迎提出 issue 與 pull request。開發環境設定、變更前必須通過的把關檢查，以及測試套件強制執行的慣例，見 [CONTRIBUTING.md](../../CONTRIBUTING.md)。

## 安全性

Anti-REA 本身的安全弱點，請透過 [SECURITY.md](../../SECURITY.md) 回報，不要開公開 issue。「已知限制」一節所寫的設計限制不是漏洞。
