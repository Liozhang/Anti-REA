> [!IMPORTANT]
> Anti-REA는 반드시 이 저장소에서만 받으라. 아직 npm 배포가 없으며, 이름이 비슷한
> 패키지가 존재한다고 해서 그것이 공식 배포본이라는 뜻은 아니다.
> 본인이 소유했거나 보호를 허가받은 소프트웨어에만 사용하라.

REA(Reverse Engineer Anything)와 이에 준하는 MCP 기반 도구 모음을 이용하면, 인공지능 에이전트가 소스 코드 없이 출시된 바이너리나 패키지, 애플리케이션을 조사하고 기능의 동작 방식을 설명하며 그와 같은 구현물을 직접 만들어 낼 수 있다. 이로 인해 당신이 출시하는 소프트웨어를 이해하는 비용은 거의 0에 가까워진다.

Anti-REA는 방어자를 위한 대응 수단이다. 같은 작업 흐름을 공유하는 명령줄 인터페이스를 함께 갖춘 MCP 서버로서, **당신의 프로젝트**를 출시에 앞서 강화한다:

- **audit_artifact**: 출시된 산출물이 그러한 도구들이 사용하는 리더와 엔진에 노출하는 것. 모든 사실의 근거와 출처 범위가 함께 제공된다.
- **harden_artifact**: 이 도구가 적용할 수 있는 완화 조치의 적용. 외부 도구나 아키텍처 변경이 필요한 조치는 함께 보고된다.
- **verify_artifact**: 완화 조치가 실제로 유효한지의 확인.
- **generate_notice**: 당신의 산출물 자체 README에 넣을 진실한 라이선스 문안과 역공학 금지 문안의 생성. 이렇게 하면 조사 중인 에이전트가 권한을 확인하는 바로 그 순간, 당신의 조건을 데이터로 마주한다.
- **generate_probe_kit**: 당신의 코드에 넣어 쓸 수 있는 런타임 관측 탐지 패키지와 수동 점검 목록.

## 작동 원리

세 가지 명령이 순서대로 실행되며, 그 순서가 의미를 갖는다:

1. **`audit`**(감사)는 산출물을 실행하지 않고 읽어, 리더가 추출할 수 있는 모든 사실을 보고한다. 각 사실에는 근거가 되는 범위와 그것을 사용할 리더가 함께 제시된다. 감사는 산출물에 아무것도 쓰지 않는다.
2. **`harden`**(강화)는 그 보고서를 받아 적용 가능한 완화 조치를 적용하고, 원본 옆에 `.hardened` 사본을 쓴다. 모든 완화 조치는 동일 길이 덮어쓰기 또는 재배치 쓰기이므로, 파일 길이와 오프셋이 그대로 유효하다. 런타임 동작을 바꿀 수 있는 조치는 사유와 함께 건너뛴 것으로 보고되며, 결코 조용히 시도하지 않는다. 결과의 모든 항목은 적용되었든 건너뛰었든, 그 완화 조치를 적용한 뒤에도 남는 노출과 그 노출을 완전히 없애는 빌드 시 수정을 함께 밝힌다. 적용된 조치가 완전한 조치로 보고되는 일은 없다.
3. **`verify`**(검증)는 강화된 사본을 다시 읽어 사용자가 여전히 의존하는 구조를 확인한다. 필수 구조 집합은 적용된 완화 조치에서 도출된다. 조치가 건드린다고 선언한 것은 면제되고, 그 외의 것은 모두 파싱 가능한 상태를 유지해야 한다. 필수 구조를 파괴한 강화 실행은 검토에 실패하며, 원본은 그대로 남는다.

이 세 가지 작업 흐름이 MCP 도구와 명령줄 인터페이스를 동시에 뒷받침한다. 따라서 에이전트와 터미널은 같은 제품에 대해 같은 결론에 이른다. 종료 코드는 터미널의 약속이다. 감사나 강화가 정상적으로 완료되면 0, 검증이 실패하면 1, 사용법 오류는 2, 거부는 3이다. MCP에는 종료 코드가 없다. 0은 `isError: false`에 대응하고 보고서는 결과와 함께 반환된다. 1, 2, 3은 모두 `isError: true`에 대응한다. 거부는 성공이 아니며, 거부 보고서에도 `status: "refused"` 와 빠진 필드를 하나하나 짚어 주는 `omitted_reason` 이 담겨 있다.

## 에이전트 연결

MCP를 지원하는 임의의 에이전트(Claude Code, Cursor, Codex 등)에 이 서버를 등록한다:

```json
{
  "mcpServers": {
    "anti-rea": {
      "command": "node",
      "args": ["/absolute/path/to/Anti-REA/bin/anti-rea-mcp.js"]
    }
  }
}
```

그런 다음 에이전트에게 이렇게 요청한다: */path/to/app 에 있는 내 앱을 audit 해서 무엇이 노출되는지 알려 줘.*

## 터미널에서 빠르게 시작하기

```bash
node bin/anti-rea.js audit /absolute/path/to/your/app --json
node bin/anti-rea.js harden /absolute/path/to/your/app --from audit.json
node bin/anti-rea.js verify /absolute/path/to/your/app
node bin/anti-rea.js notice --template license > NOTICE.md
node bin/anti-rea.js probe /absolute/path/to/probe-kit-output
```

`probe` 명령은 런타임 관측 저항 계층을 위한 통합 패키지를 쓴다. 관측 가능한 사실에 대한 탐지 코드 조각과 수동 점검 목록이 들어 있다. 이 명령은 지정한 디렉터리에만 쓰고 당신의 산출물은 절대 수정하지 않는다. 에이전트는 `generate_probe_kit` 도구로 같은 패키지를 받을 수 있다.

## 감사가 보고하는 내용

| 노출 대상 | 누가 읽는가 | 감사가 보고하는 내용 |
| --- | --- | --- |
| ELF/PE/Mach-O 헤더, 섹션, 심볼, 빌드 ID | 내장 정적 리더, objdump | 리더가 추출할 수 있는 모든 사실과 그 출처 범위 |
| 내장된 Go 모듈 및 빌드 메타데이터 | 내장 Go 리더 | 존재 여부, 버전, 그리고 이를 담고 있는 섹션 |
| 내장된 Rust 의존성 메타데이터(`.dep-v0`) | 내장 Rust 리더 | 크레이트 이름, 버전, 의존성 관계 |
| Android DEX 타입 서술자, 메서드명, 문자열 상수 | 내장 DEX 리더 | 클래스명, 메서드명, 상수 풀 |
| PE 인증서, 임포트, 익스포트, 로드 설정 | 내장 PE 리더 | 서명자 신원과 선언된 임포트 |
| 모델, Erlang, pyc 등 컨테이너 메타데이터 | 내장 포맷 리더 | 선언된 메타데이터와 총계 |
| 내장된 자격 증명 | 토큰 패턴 스캐너 | 공개된 형식을 가진 알려진 자격 증명 계열과 그 오프셋 |

리더 세트 밖의 형식은 건너뛰지 않고 보고된다. 감사가 Unity IL2CPP의 `global-metadata.dat`, .NET 어셈블리, JavaScript 번들, APK 서명 블록, 또는 GPU 페이로드 컨테이너를 만나면, 빈 결과를 반환하는 대신 그 형식을 능력 경계로 지목하고, 지원 범위를 벗어나는 사유와 그다음에 취할 조치를 함께 알린다. 빈 결과는 안전의 증거가 아니다. APK는 ZIP으로 읽힌 다음 한 단계 더 따라간다. `classes.dex`의 각 항목은 저장된 것이든 압축된 것이든 DEX 리더에 전달되므로, 앱의 클래스명, 메서드명, 문자열 상수가 `app.apk!classes.dex` 경로로 보고서에 들어간다. 서명 블록은 파싱되지 않고 능력 경계로 보고된다.

모든 발견 항목에는 근거, 그것을 사용할 리더, 그것을 제거할 완화 조치, 그 완화 조치를 적용한 뒤에도 남는 노출, 그리고 그 노출을 완전히 없애는 빌드 시 수정이 함께 담긴다.

## 실측 결과

아래 내용은 모두 픽스처가 아닌 실제 산출물로 실행한 결과다. Linux용과 Windows용으로 각각 빌드한 Go 1.24.4 바이너리와 Python 3.13 바이트코드 파일을 이 도구로 강화한 뒤, REA 자체의 정적 리더와 새로 투입된 에이전트로 다시 읽었다.

| 질문 | 결과 |
| --- | --- |
| 강화한 뒤에도 REA가 Go 빌드 정보를 복원하는가? | 아니오. ELF와 Windows PE 모두에서 `inspect-go-binary`는 인식된 Go 빌드 정보 레코드를 찾지 못했다고 보고한다. 강화 전에는 이 도구가 모듈 경로, 버전, 여섯 개의 빌드 설정을 반환했다. |
| ELF 심볼 테이블과 빌드 ID가 사라졌는가? | 예. `.symtab`은 섹션 테이블에서 완전히 제거되고, GNU 빌드 ID 설명자는 PT_NOTE 세그먼트와 SHT_NOTE 섹션 모두에서 0으로 덮어써진다. note 구조 자체는 파싱 가능한 상태로 남는다. |
| 일반 `strings`로도 모듈 이름을 찾을 수 있는가? | 예. 모듈 이름, 컴파일러 버전, 빌드 설정이 읽기 전용 데이터와 함수 이름 테이블에 그대로 남는다. '알려진 한계'를 참조하라. |
| 감사가 Python 바이트코드에 숨겨진 토큰을 찾아내는가? | 예, 이번 배포부터 가능하다. 토큰 스캐너는 아홉 가지 형식 전체를 대상으로 실행되며, 내장된 자격 증명은 보고되고 요청 시 덮어써진다. |
| 법적 고지가 조사 중인 에이전트를 멈추게 하는가? | 실측 샘플에서는 아니오. 네 명의 새로 투입된 에이전트가 동일한 바이너리에 대해 같은 역공학 과제를 받았고, 둘은 생성된 고지를 보고 둘은 보지 못했다. 네 명 모두 분석을 완료했다. 고지를 읽은 두 에이전트는 모두 그것을 인용하며, 분석 결과를 재배포하려면 승인이 필요하다고 스스로 밝혔다. |
| 강화한 뒤에도 무엇이 계속 노출되는가? | 제거되지 않은 디버그 정보에 남아 있는 빌드 머신 경로, PE 임포트 테이블, 그리고 소프트웨어가 실행되기 위해 필요한 모든 형식 관련 사실이다. 감사는 이들을 완화 조치를 지어내지 않고 그대로 보고한다. |

다섯 번째 행이 가장 솔직한 결과다. 고지 계층은 에이전트가 그 작업을 어떻게 틀 짓는지는 바꾸지만, 실행 여부를 바꾸지는 않는다. 이를 기술적 장벽이 아니라 계약이자 추적 가능성 확보 수단으로 다루어야 한다.

## 감사 출력물 보호하기

감사 보고서는 당신의 산출물이 어디에 노출되어 있는지, 그리고 어떤 완화 조치가 적용되었는지를 보여 주는 지도다. 이를 버전 관리에 커밋하거나 산출물 안에 포함해 출시하면, 저장소를 읽는 사람 누구에게나 그 지도를 넘겨 주는 셈이 된다. 출력 경로가 git 작업 트리 안에 있을 때 Anti-REA는 표준 오류로 경고를 쓴다. 보고서를 협력사, 감사인 또는 취약점 공개 프로그램과 공유해야 한다면 `--redacted`를 사용하라. 이 옵션은 분류와 개수는 유지하고 정확한 경로, 바이트 범위, 완화 조치 대응 관계는 제외한다. 생성된 고지에는 Anti-REA에 대한 언급이나 당신의 강화 상태에 대한 암시가 전혀 없다.

## 방어 계층

| 계층 | 도구 | 기대 효과 | 잔존 위험 |
| --- | --- | --- | --- |
| 메타데이터 정리 | `audit_artifact`, `harden_artifact` | 내장 리더가 사실 대신 '알 수 없음'을 반환한다 | 새로운 리더가 새로운 형식을 노릴 수 있다. 일반 문자열 검색은 읽기 전용 데이터에서 모듈 이름과 버전을 여전히 찾아 낸다 |
| 내용 보호 | `harden_artifact` | 직접 지정한 바이트 범위만 0으로 덮어쓸 뿐이며, 어떤 감사 발견도 이 조치를 도출하지 않는다 | 그 범위 밖의 모든 것은 손대지 않아 그대로 읽을 수 있다 |
| 런타임 관측 저항 | `generate_probe_kit` | 디버거와 계측의 비용을 높인다 | 커널 수준의 관측은 막을 수 없다 |
| 에이전트 중단 조건 유도 | `generate_notice` | 에이전트가 인간에게 권한을 확인한다 | 에이전트가 고지를 무시할 수 있다 |
| 모델 수준의 진실한 신호 | `generate_notice` | 권한 확인 문제를 피할 수 없게 된다 | 모델의 행동은 확률적이다 |
| 비밀 최소화 | 보고서 권고 | 유일하게 절대적인 계층 | 서버 측 아키텍처가 필요하다 |
| 법적·운영적 조치 | `generate_notice` | 계약과 추적 가능성은 바이트가 할 수 없는 일을 해낸다 | 집행은 법적 절차다 |

표의 두 행은 보호 제품이 보통 그 이름에 담는 의미와 다르며, 이 프로젝트도 그렇게 주장하지 않는다. 내용 보호는 아무것도 난독화하지 않는다. 손으로 지정한 바이트 범위를 0으로 지울 뿐이고, 그 계층에서는 어떤 리더도 발견을 내놓지 않으므로 감사에서 강화로 이어지는 경로는 결코 거기에 이르지 않는다——범위는 직접 지정해야 한다. 비밀 최소화 역시 이 도구가 적용하는 조치가 아니다. 패턴 일치로 닿을 수 있는 토큰은 처음부터 컴파일되지 말았어야 한다는 권고일 뿐이며, 비용 증가가 아니라 유일하게 절대적인 계층이다.

## 알려진 한계

다음 세 가지 한계는 실측으로 확인되었으며, 이론적 추측이 아니다:

- **일반 문자열 검색은 여전히 통한다.** 동일 길이 덮어쓰기는 Go 빌드 정보나 ELF 심볼 테이블 같은 메타데이터 레코드를 파괴한다. 하지만 모듈 이름, 컴파일러 버전, 빌드 설정은 Go 런타임이 읽는 읽기 전용 데이터와 함수 이름 테이블에도 함께 존재한다. 이 바이트를 덮어쓰면 런타임 동작이 바뀌므로, Anti-REA는 이들을 손대지 않는다. 따라서 강화된 바이너리에 `strings`를 실행하면 누구나 이 값을 되찾을 수 있다. 감사 보고서는 각 발견 항목마다 이것을 근본적으로 제거하는 빌드 플래그를 밝힌다: `-trimpath`, `-ldflags="-s -w"`, `strip`. 그 플래그 자체의 대가도 함께 알린다. 따라서 다시 빌드하기 전에 절충을 확인할 수 있다.
- **모든 노출에 완화 조치가 있는 것은 아니다.** PE 임포트 테이블, ELF 헤더의 형식 정보, Python 바이트코드 형식 플래그는 소프트웨어가 실행되기 위해 필요한 존재이므로 완화 조치 없이 보고만 된다. 감사는 가상의 대책을 지어내지 않고 이 사실을 그대로 알린다.
- **토큰 패턴은 알려진 형식만 다룬다.** 스캐너는 공개된 형식을 가진 자격 증명 계열과 대응한다. 비공개 형식의 토큰은 이 스캐너에 보이지 않으며, 결과가 비어 있다고 해서 비밀이 없다는 증거는 아니다.

지원 플랫폼 범위는 수정이 진행 중인 실측 한계다. 이 도구는 순수 Node.js로 작성되어 네이티브 의존성이 없지만, 테스트 스위트와 픽스처는 지금까지 Windows에서만 수동으로 실행되었다. 이제 GitHub Actions 워크플로가 모든 푸시에서 Ubuntu, macOS, Windows에 걸쳐 같은 세 가지 검사를 실행한다. 해당 워크플로가 어떤 커밋에서 완료되기 전까지는 macOS와 Linux를 검증된 것이 아니라 동작할 것으로 예상되는 것으로 취급하라.

## 자주 묻는 질문

<details>
<summary><strong>강화가 내 애플리케이션을 손상시킬 수 있는가?</strong></summary>

완화 조치는 동일 길이 덮어쓰기 또는 전체 재배치이며, 재배치 시 모든 형식 검사를 다시 실행한다. 사용자가 의존하는 구조를 파괴한 강화 실행은 `verify`에서 실패한다. 런타임 동작을 바꿀 수 있는 조치는 시도하지 않고 사유를 명시하여 건너뛴다. 이미 강화된 산출물에 `harden`을 다시 실행하면 아무것도 바뀌지 않는다고 보고할 뿐이다. 그리고 바이트 단위 조치는 어느 것도 완전하지 않으므로, 결과의 모든 항목은 적용한 뒤에도 남는 노출을 밝힌다. 실행이 끝났다고 부르기 전에 그 줄을 읽어라.

</details>

<details>
<summary><strong>이 도구가 내 바이너리를 어딘가에 업로드하는가?</strong></summary>

아니다. 모든 읽기와 쓰기는 프로세스 내부의 로컬 파일 연산이다. 네트워크 요청도, 자식 프로세스도, 원격 측정도 없다.

</details>

<details>
<summary><strong>어떤 에이전트가 사용할 수 있는가?</strong></summary>

로컬 MCP 서버를 등록할 수 있는 모든 에이전트가 해당한다. Claude Code, Cursor, Codex 등이 그 예다. 수동 등록 방법은 '에이전트 연결' 절의 JSON 블록이다.

</details>

<details>
<summary><strong>감사 보고서 자체가 유출인가?</strong></summary>

그렇다. 그래서 이 도구는 보고서를 git 작업 트리 안에 쓸 때 경고하고 `--redacted`를 제공한다. 이 옵션은 분류와 개수는 유지하고 정확한 경로, 바이트 범위, 완화 조치 대응 관계는 제외한다.

</details>

<details>
<summary><strong>감사가 아무것도 찾지 못하면 어떻게 되는가?</strong></summary>

그 경우 산출물은 리더가 추출할 만한 것을 아무것도 노출하지 않으며, 보고서는 그 한계와 함께 그 사실을 밝힌다. 다만 빈 결과가 안전의 증거는 아니다. 토큰 패턴은 알려진 자격 증명 형식만 다루며, 새로운 리더가 새로운 형식을 노릴 수 있다.

</details>

<details>
<summary><strong>집요한 역공학자를 막을 수 있는가?</strong></summary>

아니다. 이 도구는 자동화된 리더의 비용을 높이고 당신의 법적 입장을 뒷받침할 증거를 남길 뿐이다. 디버거를 다루는 숙련된 사람이나 커널 수준 접근 권한을 가진 사람은 파일 안의 바이트로는 막을 수 없는 범위에 있다. 클라이언트에 비밀을 두지 않는 것만이 유일하게 절대적인 계층이다.

</details>

<details>
<summary><strong>고지가 정말로 에이전트를 멈추게 하는가?</strong></summary>

믿을 만하지 않으며, 이 프로젝트도 그렇게 주장하지 않는다. 새로 투입된 네 명의 에이전트를 대상으로 한 실측 샘플에서 멈춘 에이전트는 없었다. 고지를 읽은 두 에이전트는 모두 그것을 인용하며, 분석 결과를 재배포하려면 승인이 필요하다고 지적했다. 고지를 계약이자 추적 가능성 확보 수단으로 다루어라.

</details>

<details>
<summary><strong>버그를 발견했다면 어떻게 해야 하는가?</strong></summary>

최신 커밋을 사용하고 있는지 확인한 뒤, Node 버전, 대상 형식, 실행한 명령, 출력을 함께 적어 이슈를 등록하라. '기여하기'를 참조하라.

</details>

## 경계

Anti-REA는 설계상 다음을 하지 않는다:

- **프롬프트 주입을 하지 않는다.** 이 도구는 에이전트 지시 파일(`AGENT.md`, `CLAUDE.md`, `.cursorrules` 등)을 당신의 산출물에 포함시키지 않으며, 인공지능 에이전트를 향한 지시문을 작성하지 않는다. 고지는 인간 독자를 향한 사실 진술이며, README, LICENSE, NOTICE, 버전 리소스와 같은 데이터 채널을 통해서만 전달된다.
- **법적 주장을 꾸며 내지 않는다.** 생성된 고지 문구의 모든 줄은 실제 조항이거나 실제로 확인 가능한 사실이다. 부풀려진 위협은 누군가 확인하는 순간 힘을 잃는다.
- **합법적인 사용자를 해치지 않는다.** 완화 조치는 당신의 소프트웨어 동작을 약화시키지 않는다. 런타임 보호는 위협 모델에 따라 선택적으로 켜는 것이며, 기본값이 아니다.

## 이 저장소에 관하여

Anti-REA는 처음부터 공개 소스로 설계되었다. 감사 규칙은 공개되어 있고, 저장소에는 비밀이 없으며, 공격 페이로드도 담겨 있지 않다. 이 도구의 가치는 자동화와 증거에 있으며, 비밀 유지에 있지 않다. 유일하게 절대적인 방어 계층인 클라이언트에 비밀을 두지 않는 원칙은, 누구든 이 코드를 읽더라도 영향을 받지 않는다. 다만 저장소에 절대 들어가서는 안 되는 것이 하나 있으니, 바로 특정 사용자를 위한 감사 출력물이다. 이를 위해 이 도구는 관련 경고를 표시하고 `--redacted`를 제공한다.

## 검증

모든 기능은 실제 픽스처 파일을 이용한 `node --test`로 검증되며, MCP 인터페이스는 표준 stdio 핸드셰이크를 통한 스모크 테스트로 점검된다:

```bash
node --test
node scripts/mcp-smoke.mjs
node tests/fixtures/build.mjs --check
```

현재 스위트는 595개 테스트로, 모두 통과하며, 여기에 픽스처 다이제스트 등록 점검이 추가된다. 이 스위트는 Windows에서 수동으로 실행되었고, Ubuntu, macOS, Windows에서는 CI 워크플로로 실행되었다. Node.js는 22와 24이다.
